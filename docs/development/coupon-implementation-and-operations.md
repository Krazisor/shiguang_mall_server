# 时光商城优惠券实现、运营、权限与风控规范

## 1. 文档目的

本文把优惠券产品、数据库和 API 契约转化为可执行的角色分工、运营流程、页面能力、指标口径、风控规则、定时任务和故障处理方案。它解决以下问题：

1. 平台、商家和买家分别能做什么，哪些动作必须隔离。
2. 一场活动从设计、配置、校验、发布到结束如何执行。
3. 如何解释用户“领不到、用不了、退款为什么没返券”等问题。
4. 如何发现超发、重复核销、金额分摊或商家结算差异。
5. 如何在不绕过交易、钱包和售后状态机的前提下恢复异常。

## 2. RBAC 设计

### 2.1 新增权限

| 权限代码 | 作用域 | 典型资源 | 允许动作 |
| --- | --- | --- | --- |
| `coupon:read:self` | `PLATFORM` | `/api/coupon-center/**`、`/api/coupons/**` | 查看本人可领取活动、本人券和适用商品 |
| `coupon:claim` | `PLATFORM` | 领取、抢券、兑换 | 产生本人用户券 |
| `shop:coupon:read` | `SHOP` | `/api/shops/{shopId}/coupon-**` | 查看本店模板、活动、核销、优惠订单和报表 |
| `shop:coupon:manage` | `SHOP` | 本店活动/模板写接口 | 创建、编辑、发布、暂停、恢复、结束、复制 |
| `shop:coupon:grant` | `SHOP` | 本店发券和兑换码批次 | 定向发券、生成/撤销未兑换代码 |
| `shop:coupon:funding:approve` | `SHOP` | 联合承担邀请 | 接受或拒绝平台活动中本店承担比例 |
| `platform:coupon:read` | `PLATFORM` | `/api/platform/coupon-operations/**` | 跨店只读、报表和业务追踪 |
| `platform:coupon:manage` | `PLATFORM` | 平台活动/模板写接口 | 创建平台券、平台活动和联合承担规则 |
| `platform:coupon:grant` | `PLATFORM` | 平台发券和兑换码批次 | 定向发平台券、生成代码 |
| `platform:coupon:governance` | `PLATFORM` | `/api/platform/coupon-governance/**` | 暂停违规店铺活动、解除治理暂停、撤销未使用券 |

权限作用域必须与角色作用域一致。不能把 `shop:coupon:*` 授给 `PLATFORM` 角色，也不能把 `platform:coupon:*` 授给 `SHOP` 角色。

### 2.2 建议角色

| 角色代码 | 作用域 | 建议权限 | 说明 |
| --- | --- | --- | --- |
| `CUSTOMER` | `PLATFORM` | `coupon:read:self`、`coupon:claim` | 现有普通用户增量授权 |
| `SHOP_ADMIN` | `SHOP` | 四个店铺优惠券权限 | 本店最终管理责任人，默认可接受联合承担 |
| `SHOP_MARKETING_OPERATOR` | `SHOP` | `shop:coupon:read/manage/grant` | 建议新增的店铺营销运营种子角色；默认不能承诺店铺承担 |
| `PLATFORM_COUPON_OPERATOR` | `PLATFORM` | `platform:coupon:read/manage/grant` | 平台营销配置与发放 |
| `PLATFORM_COUPON_GOVERNOR` | `PLATFORM` | `platform:coupon:read/governance` | 平台治理，不负责创建营销规则 |
| `SUPER_ADMIN` | `PLATFORM` | 可增量授权全部平台优惠券权限 | 仍不能绕过店铺成员边界 |

`PLATFORM_SHOP_ADMIN` 不默认获得优惠券治理权限。店铺治理和营销治理涉及不同数据与风险，确需兼任时由 `SUPER_ADMIN` 明确分配角色。

角色管理已有自定义角色能力。若课程范围不希望增加种子角色，可创建同名职责的自定义角色，但权限组合和数据范围不得改变。

### 2.3 职责分离

| 动作 | 买家 | 店铺营销 | 平台运营 | 平台治理 | 超级管理员 |
| --- | --- | --- | --- | --- | --- |
| 领取/兑换本人券 | 是 | 作为买家身份可做 | 作为买家身份可做 | 作为买家身份可做 | 作为买家身份可做 |
| 创建店铺券 | 否 | 本店 | 否 | 否 | 仅成为目标店铺有效成员且有店铺权限 |
| 创建平台券 | 否 | 否 | 是 | 否 | 有平台管理权限时是 |
| 定向发店铺券 | 否 | 本店 | 否 | 否 | 不因平台身份自动允许 |
| 定向发平台券 | 否 | 否 | 是 | 否 | 有平台发券权限时是 |
| 接受联合承担 | 否 | 仅有资金确认权限的本店管理员 | 发起邀请但不能代接受 | 否 | 仍需目标店铺有效成员身份 |
| 暂停本店活动 | 否 | 是 | 否 | 可治理暂停任意店铺活动 | 不自动走店铺接口 |
| 恢复治理暂停 | 否 | 否 | 否 | 是 | 有治理权限时是 |
| 撤销未使用券 | 本人不可撤销 | 否 | 否 | 是 | 有治理权限时是 |
| 查看跨店核销 | 否 | 仅本店 | 是 | 是 | 有只读权限时是 |
| 修改订单/钱包金额 | 否 | 否 | 否 | 否 | 否，必须走交易/售后/结算专用流程 |

“能看见资源”不等于“能执行动作”。按钮由 `availableActions` 和权限共同控制，后端始终重新鉴权。

## 3. 店铺数据范围

所有店铺优惠券接口必须同时校验：

1. 当前账号为 `ACTIVE` 且未删除。
2. 路径店铺存在。
3. `shop_user(shop_id,user_id)` 为 `ACTIVE`。
4. 店铺角色与目标权限均为 `ACTIVE` 且作用域为 `SHOP`。
5. Mapper 查询包含同一个 `shop_id`，不能校验路径后只按裸 `activityId/templateId` 查询。
6. 店铺券模板 `owner_shop_id` 等于路径店铺。
7. SPU/SKU 范围目标也属于同一店铺。

接受联合承担时还要锁定参与关系并确认其中 `shop_id` 等于路径店铺；平台创建者、其他店铺人员和普通营销运营不能代替店铺管理员决定。

越权读取其他店铺资源统一返回 `RESOURCE_NOT_FOUND`，避免泄露活动或模板是否存在。已公开活动只能从买家领券中心读取公开字段，不能借公开 ID 访问管理详情和预算。

## 4. 运营配置流程

### 4.1 活动立项

运营在创建活动前必须回答：

| 主题 | 必填决策 |
| --- | --- |
| 目标 | 拉新、首单转化、店庆促销、召回或客服补偿 |
| 归属 | 平台活动或某一店铺活动 |
| 活动类型 | 常规领券、限时抢券、新客欢迎、定向活动 |
| 时间 | 开始、结束、领取窗和券使用窗 |
| 人群 | 全部用户、新用户、首单用户或指定用户 |
| 商品范围 | 全部、指定店铺、类目、SPU 或 SKU |
| 券种 | 百分比、满减、零门槛红包 |
| 叠加 | 独占或允许跨归属叠加 |
| 资金 | 平台、商家或联合承担 |
| 规模 | 总发行量、单用户限领、最大责任预算 |
| 退款 | 不返券或全父交易退款返券 |

未明确以上任一项不得使用描述文案代替结构化配置。

### 4.2 配置顺序

推荐顺序：

~~~mermaid
flowchart LR
    A["创建活动草稿"] --> B["创建券模板"]
    B --> C["配置范围"]
    C --> D["校验预算与时间"]
    D --> E["预览用户展示"]
    E --> F["激活模板"]
    F --> G["发布活动"]
    G --> H["监控领取与核销"]
    H --> I["结束与复盘"]
~~~

活动可以先建，模板也可以不属于活动用于定向发放。面向用户领取的模板必须先激活，再发布包含它的活动。

### 4.3 发布前检查

系统校验之外，运营必须人工确认：

1. `percentageOff` 是“减免百分比”而不是折后比例。
2. 满减门槛和券面金额与展示文案完全一致。
3. 平台/店铺归属和资金承担没有填反。
4. 范围选择器中的商品确实为目标商品，抽查至少 3 个命中和 3 个不命中样本。
5. 固定有效期晚于领取结束；相对有效期文案与小时数一致。
6. 单用户限领、总发行量和预算满足最坏责任。
7. 是否允许与另一归属券叠加符合活动目的。
8. 联合承担模板的目标店铺集合与范围完全一致，且全部店铺已明确接受比例。
9. 零门槛红包可能只部分使用的提示已经配置。
10. 退款返券政策明确，客服知识库有同一口径。
11. 店铺状态为 `ACTIVE`，活动横幅资源归属正确。

### 4.4 模板复制

复制用于复用配置，不继承以下运行数据：

- 模板编号；
- 状态和版本；
- 已发行量；
- 预算已预占/消耗/冲回；
- 第一张发行时间；
- 用户券、领取、兑换码、核销和操作历史。

复制后固定为 `DRAFT`。运营必须重新检查时间、预算和范围；不能把“复制成功”理解为“可直接发布”。

## 5. 限时抢券运营

### 5.1 上线前容量准备

- 根据 `totalIssueLimit`、预计峰值 QPS 和单用户限领准备压测数据。
- Redis 限流和报价缓存不可用时，限时抢券应快速返回依赖错误，不能放弃限流直接压向数据库。
- 数据库最终使用模板条件更新和唯一约束，Redis 剩余量只作近似展示。
- 活动开始前完成服务端时间校准和多实例时钟检查，业务时区统一 `Asia/Shanghai`。
- 至少执行一次“用户连点、双端同时抢、相同 Key 重试、不同 Key 并发、最后一张竞争”测试。

### 5.2 活动中观察指标

| 指标 | 观察意义 |
| --- | --- |
| 领取请求 QPS / P95 / P99 | 接口容量和排队情况 |
| 领取成功率 | 需拆分售罄、限领、风控、依赖失败，不能只看总失败 |
| 数据库条件更新失败数 | 售罄竞争是否符合预期 |
| 同用户限领冲突数 | 重复点击或自动化请求强度 |
| Redis 与数据库剩余量差异 | 缓存延迟；数据库值为权威 |
| 用户券创建与领取记录差异 | 事务异常或数据缺陷，必须为 0 |
| 模板预算预占与用户券责任差异 | 预算聚合错误，必须为 0 |

### 5.3 售罄体验

售罄后活动和模板仍可查看，按钮稳定显示“已抢完”。前端不每秒轮询精确库存；用户主动刷新或活动推送更新即可。运营不能通过临时提高缓存库存“补券”，必须增加模板 `totalIssueLimit` 和 `budgetAmount`，由版本控制和操作日志记录。

## 6. 买家体验规则

### 6.1 不可领取/使用说明

| 原因代码 | 用户说明方向 | 建议下一步 |
| --- | --- | --- |
| `NOT_STARTED` | 活动尚未开始 | 展示服务端倒计时 |
| `ACTIVITY_PAUSED` | 活动暂时不可领取 | 稍后查看，不承诺恢复时间 |
| `ACTIVITY_ENDED` | 活动已经结束或取消 | 查看其他活动 |
| `SOLD_OUT` | 本轮已领完 | 查看其他券 |
| `USER_LIMIT_REACHED` | 已达到限领，可去“我的券”查看 | 打开我的优惠券 |
| `AUDIENCE_NOT_ELIGIBLE` | 当前账号不符合活动人群 | 查看其他活动 |
| `ACCOUNT_UNAVAILABLE` | 当前账号状态不允许领券 | 进入账号状态处理，不提示营销重试 |
| `NOT_EFFECTIVE` | 券尚未生效 | 展示准确生效时间 |
| `EXPIRED` | 券已经过期 | 查看其他可用券 |
| `REVOKED` | 券已按治理规则撤销 | 展示客服入口和可公开原因，不展示风控细节 |
| `THRESHOLD_NOT_MET` | 当前有效商品金额不足 | 展示差额和可用商品 |
| `SCOPE_MISMATCH` | 当前商品不在适用范围 | 查看适用商品 |
| `STACK_CONFLICT` | 与已选券不能同用 | 让用户二选一并展示各自优惠 |
| `LOCKED_BY_OTHER_TRADE` | 券正在另一待支付订单中 | 跳转对应交易 |
| `FIRST_ORDER_TRADE_EXISTS` | 已有一笔首单券待支付交易 | 跳转该交易支付或取消 |
| `FIRST_ORDER_QUALIFICATION_LOST` | 已完成其他首单 | 刷新结算并选择其他券 |
| `QUOTE_CHANGED` | 商品、价格或券状态变化 | 一键刷新结算 |

不得把不同原因统一显示为“系统繁忙”。真正的依赖故障才使用稍后重试，并保留用户当前购物车和选择。

### 6.2 自动推荐

结算页默认主动发送 `mode=AUTO`；旧客户端省略字段仍为无券。页面必须允许：

- 查看推荐组合为何省得最多；
- 改选另一合法组合；
- 明确选择不使用；
- 查看不可用券和门槛差额；
- 在提交前确认优惠前金额、优惠、应付。

用户手选合法但非最优方案时，不弹窗强迫换回。可以显示“另有方案可多省 X 元”，但最终尊重用户确认。

### 6.3 券锁定说明

创建待支付交易后，用户券显示“使用中”，并可跳转关联父交易。支付失败但交易仍可支付时不释放券；取消或超时后状态自动恢复。客服不能通过后台直接把 `LOCKED` 改为 `AVAILABLE`，必须先核对父交易状态并运行预占恢复任务。

## 7. 退款与客服口径

### 7.1 退款金额解释

客服统一解释：

~~~text
退款上限按该商品优惠后的实际支付金额计算。
优惠券抵扣部分不是现金支付，不会额外退入钱包。
~~~

示例：商品原价 100 元，分摊优惠 20 元，实付 80 元；全退钱包最多退 80 元，不是 100 元。

### 7.2 返券解释

默认 `FULL_TRADE_ONLY`：

- 单件部分退、单个店铺子订单全退但跨店父交易未全退：不返券。
- 父交易所有明细全额退款成功：符合模板政策的券返还一次。
- 返券截止时间至少为返还后 72 小时。
- 同一用户券退款返还最多一次；再次使用后再次全退不返。
- 首单券在用户已完成其他首单时不返。
- 被风控撤销的券不返。

客服页面应直接显示 `couponRestoreHint` 和最终返券结果，不要求客服手工汇总多个子订单判断。

### 7.3 客服禁止动作

客服不得：

- 修改用户券状态字段；
- 修改订单 `coupon_discount_amount`；
- 用模拟钱包充值代替正常返券或退款；
- 删除核销/分摊/预算流水；
- 通过重新发同模板绕过单用户限领；
- 让商家用人工调账掩盖平台补贴差异。

需要补偿时由有 `grant` 权限的人员使用专门 `DIRECT_GRANT` 模板，并填写工单号和原因。

## 8. 指标口径

### 8.1 发行漏斗

| 指标 | 公式 |
| --- | --- |
| 计划发行量 | `coupon_template.total_issue_limit` |
| 已发行量 | `coupon_template.issued_count` |
| 当前可用券数 | 实时 `AVAILABLE` 且 `validFrom<=now<validTo` 的用户券数 |
| 已锁定券数 | `user_coupon.status=LOCKED` |
| 已核销券次数 | `coupon_redemption.consumed_at IS NOT NULL` 的记录数；`RESTORED` 保留原核销一次，返券后再次使用的 `attemptNo=2` 再计一次 |
| 领取率 | 已发行量 / 计划发行量 |
| 核销率 | 至少存在一次 `consumed_at` 的去重用户券数 / 已发行用户券数 |
| 过期率 | 未使用即过期用户券数 / 已发行用户券数 |

报表必须注明分母为 0 时返回 `null`，不返回无意义的 0% 或除零错误。

### 8.2 交易效果

| 指标 | 公式 |
| --- | --- |
| 优惠前成交额 | 已成功支付优惠交易的 `trade_order.gross_amount` 合计 |
| 买家实付 | `trade_order.payable_amount` 合计 |
| 优惠金额 | `coupon_redemption.discount_amount` 的成功核销合计减退款冲回 |
| 平台补贴 | 核销平台承担合计减 `platform_funding_reversal_amount` |
| 商家让利 | 核销商家承担合计减对应退款冲回的营销效果口径 |
| 用券订单数 | 成功支付且至少一条核销记录 `consumed_at IS NOT NULL` 的父交易去重数；返券不抹去历史成交归因 |
| 客单价 | 买家实付 / 用券父交易数 |
| 带动商品数 | 用券父交易中订单明细数量合计 |

“优惠金额”不能用 `grossAmount-payableAmount` 跨全库直接统计后忽略取消交易；只统计成功支付，并按成功退款冲回。

### 8.3 预算指标

~~~text
当前责任 = budgetReservedAmount
累计使用 = budgetConsumedAmount
累计退款冲回 = budgetReversedAmount
当前净消耗 = 累计使用 - 累计退款冲回
剩余可承担 = budgetAmount - 当前责任 - 当前净消耗
~~~

预算是营销责任和效果台账，不是钱包余额；不能用商家钱包流水反推模板预算。

## 9. 风控规则

### 9.1 基础资格

- 账号必须 `ACTIVE` 且未删除。
- 新用户按注册时间判断，不以手机号、IP 或设备作为唯一身份。
- 首单用户在领取和使用时均检查成功支付父交易。
- 指定用户模板不出现在公开领券入口。
- 同一模板按用户 ID 执行限领，设备/IP 只用于辅助限流。

### 9.2 请求风控

- 领取、兑换和带券下单使用统一 `IdempotencyService`。
- 兑换码连续错误进入短时冷却，错误响应不暴露代码状态。
- 不在业务日志保存完整兑换码、`satoken`、Redis Key、完整手机号或地址。
- 风控拒绝记录规则代码、用户 ID、模板 ID、请求 ID 和时间，不记录设备原始标识；如需要设备维度，仅保存带轮换盐的摘要并另行制定保留期限。

### 9.3 运营风险

- 百分比券必须有最高优惠金额。
- 预算必须覆盖总发行量的最坏责任。
- 已发行模板不可修改面额、范围、资金承担和返券政策。
- 平台补贴/联合承担只允许平台管理权限配置。
- 店铺券固定商家承担，避免店铺擅自承诺平台资金。
- 联合承担只允许明确店铺/SPU/SKU 范围，每个目标店铺必须由资金确认权限成员接受；平台不能代接受。
- 平台治理暂停不会撤销已领取权益；批量撤销需另行设计审批，第一版不开放。

## 10. 监控与告警

### 10.1 必须告警

| 告警 | 条件 | 严重性 |
| --- | --- | --- |
| 券超发 | `issued_count > total_issue_limit` 或用户券数大于计数 | P0 |
| 一券多活动核销 | 同一用户券存在两条活动 `RESERVED/CONSUMED` | P0 |
| 订单优惠不平 | 父/子/明细优惠求和不等 | P0 |
| 支付状态不齐 | 交易已支付但券仍 `LOCKED/RESERVED` 超过短暂事务窗口 | P1 |
| 取消未释放 | 交易已取消但券仍 `LOCKED` | P1 |
| 退款冲回重复/缺失 | 固定 `refundNo` 与退款分摊不一致 | P1 |
| 商家结算不平 | 平台补贴、商家让利与结算字段不等 | P1 |
| 预算不平 | 模板聚合与预算流水不等 | P1 |
| 联合承担集合不平 | 模板目标店铺与已接受参与关系不一致 | P1，模板不得激活 |
| 抢券依赖异常 | Redis/MySQL 错误率连续超过阈值 | P1 |
| 报价变化率异常 | `COUPON_QUOTE_CHANGED` 突增 | P2，可能是价格频繁变化或 TTL 过长 |

### 10.2 日志字段

关键日志至少包含：

~~~text
requestId, action, operatorType, operatorId,
activityNo, templateNo, couponNo, redemptionNo,
tradeNo, orderNo, refundNo, resultCode
~~~

不适用字段省略。日志金额可以记录汇总值，但不能记录完整请求体或明文兑换码。

## 11. 异常处理手册

### 11.1 活动疑似超发

1. 平台治理暂停活动，阻止新领取。
2. 对比模板 `issued_count`、用户券数、领取记录和预算流水。
3. 确认是缓存显示误差还是数据库真实超发。
4. 数据库未超发：刷新缓存和页面剩余状态，不修改业务表。
5. 数据库真实超发：保留证据并停用相关写入口；不得直接删除多出的用户券。
6. 制定带审计的补偿/撤销方案，已锁定或已使用券必须尊重交易和售后流程。

### 11.2 交易取消但券仍锁定

1. 查询父交易、核销和用户券，确认支付没有成功。
2. 运行 `recover-coupon-reservations` 的 `dryRun=true`。
3. 核对扫描目标和预期状态。
4. 运行正式恢复任务；任务沿父交易锁顺序释放。
5. 对比商品库存释放和券释放，防止只恢复一侧。

禁止直接执行 `UPDATE user_coupon SET status='AVAILABLE'`。

### 11.3 支付成功但券未核销

这是资金和权益不一致的 P1/P0 问题：

1. 暂停相关写任务，防止错误恢复券。
2. 查询支付事务是否发生部分提交；正常本地事务不应出现。
3. 检查数据库迁移、约束、异常捕获和事务传播。
4. 在明确买家已按优惠后金额支付后，通过受审计修复工具补齐核销和预算，不重新扣钱包。
5. 运行订单/核销/结算全链路对账。

### 11.4 退款完成但未返券

先判断是否真的符合返券条件：全父交易退款、模板策略、返券次数、人群和撤销状态。若不符合，向用户展示稳定原因；若符合但任务失败，使用原退款业务号重试返券步骤，唯一键保证不重复。

### 11.5 商家结算差异

1. 按订单读取优惠分摊中的平台/商家承担。
2. 校验 `buyerPaidAmount + platformCouponSubsidyAmount = grossAmount`。
3. 校验退款分摊和 `platformSubsidyRefundAmount`。
4. 校验商家钱包流水和结算聚合。
5. 只报告并定位，不使用现有平台只读接口或买家钱包调账修复。

## 12. 定时任务运维

| 任务 | 建议频率 | 关键观察 |
| --- | --- | --- |
| 开始活动 | 每 10 秒或每分钟 | 漏启动、重复状态更新 |
| 结束活动 | 每分钟 | 到期后仍成功领取必须为 0 |
| 系统事件发券 | 每分钟，按用户/模板分页 | 新注册用户欢迎券是否补发；按 `SYSTEM_GRANT:USER_REGISTERED:{userId}:{templateId}` 幂等，失败只重试/告警，不影响注册 |
| 用户券过期 | 每分钟，分批 | 状态物化延迟和预算释放 |
| 孤立预占恢复 | 每 5 分钟 | 只处理交易终态，不碰可支付交易 |
| 优惠券对账 | 每日，活动结束后可追加 | 发行、预算、订单、退款和结算差异 |

多实例任务使用统一任务锁，但每条记录仍必须有数据库状态条件和业务唯一键。任务锁丢失不能导致重复预算流水。

系统事件发券由注册成功后的异步 `USER_REGISTERED` 事件触发，定时任务只承担补偿扫描和重试。运营不得通过人工定时任务调用 `SYSTEM_GRANT`；人工补偿必须使用 `DIRECT_GRANT` 并填写工单号。营销券服务异常不能回滚注册事务，也不能让注册接口返回优惠券错误。

## 13. 后端领域归属与集成

优惠券直接参与结算、下单、支付和售后，建议归属现有 B 线交易域，包路径使用 `coupon/**`，不要放进 `order/**` 的杂项类中。B 线拥有优惠券表、Mapper、金额引擎、Controller 和任务。

A 线继续拥有身份、店铺、类目和商品。优惠券通过冻结端口读取目标和快照：

| 端口 | 提供方 | 用途 |
| --- | --- | --- |
| `ShopAccessPort` | A/shop | 复用现有店铺权限校验 |
| `ShopSummaryPort` | A/shop | 活动、模板和订单响应的店铺摘要 |
| `ProductSnapshotPort` | A/product | 结算时商品、SKU、价格、类目和店铺快照 |
| `CouponScopeTargetPort`（新增） | A/product | 草稿范围目标校验、分页摘要和店铺归属 |
| `ActiveCouponBusinessPort`（新增） | B/coupon | 店铺关闭前检查活动和锁定券 |

`CouponScopeTargetPort` 返回领域值对象，不返回 Product Mapper、实体、`Map<String,Object>` 或 Web DTO。B 线不能为方便配置范围直接导入 A 线 Mapper。

下单由订单应用服务编排商品可用性、库存预占、优惠券校验和订单创建。优惠金额引擎必须是纯领域服务，可使用固定输入做单元测试，不从算法内部查数据库或读取当前时间。

## 14. 测试矩阵

### 14.1 权限测试

1. `CUSTOMER` 能领券但不能访问任一管理接口。
2. 店铺营销人员只能操作自己的店铺，裸 ID 越权返回 `RESOURCE_NOT_FOUND`。
3. 只有 `shop:coupon:read` 的成员不能创建、发布或发券。
4. 只有 `shop:coupon:manage` 的成员不能定向发券或生成代码。
5. 店铺营销运营默认不能接受联合承担，店铺管理员可以；其他店铺不能决定本店邀请。
6. 平台只读人员不能管理平台券或执行治理。
7. 平台运营不能恢复治理人员暂停的店铺活动。
8. `SUPER_ADMIN` 未加入店铺时不能访问店铺路径。

### 14.2 规则测试

- 三券种字段组合和边界金额。
- 五种范围的命中/不命中和类目后代。
- 四种人群在领取与使用阶段的差异。
- `SYSTEM_GRANT` 仅平台新用户模板可用，活动关联与无活动两种发放条件。
- 固定/相对有效期边界 `validFrom` 和 `validTo`。
- 独占与跨归属叠加、跨三店多券。
- 自动最优并列决策。
- 最大余数分摊和一分钱尾差。
- 每子订单最低应付 `0.01`。
- 平台/商家/联合承担的分分摊。

### 14.3 并发测试

- 最后一张券 100 个并发请求。
- 同用户多 Key 并发达到 `perUserLimit`。
- 同一兑换码两名用户并发。
- 同一用户券创建两张交易。
- 支付与主动取消并发。
- 支付与超时任务并发。
- 退款重试与返券并发。
- 模板发行与运营增加发行量/预算并发。
- 注册事件消费与补偿扫描同时为同一用户发系统券。

### 14.4 全链路测试

~~~text
创建模板 -> 发布活动 -> 领取 -> 结算报价
-> 下单锁券 -> 钱包支付 -> 商家待结算
-> 部分退款 -> 全父交易退款 -> 返券
-> 预算/订单/钱包/结算对账
~~~

至少覆盖无券、店铺券、平台券、跨店叠加、零门槛红包、首单券、系统新客券和限时抢券八条路径。

## 15. 上线顺序

1. 部署 `scheme4.sql`，完成历史回填和金额约束验证。
2. 部署后端枚举、实体、Mapper、金额引擎和只读接口，写入口保持关闭。
3. 部署前端只读页面和新增响应字段兼容。
4. 启用活动/模板管理，但先只允许草稿。
5. 使用测试店铺和测试用户跑完整领取、支付、退款和结算。
6. 启用普通公开领取，小规模观察。
7. 启用定向发券和兑换码。
8. 小规模启用平台新用户 `SYSTEM_GRANT`，验证注册失败隔离、事件重试和补偿扫描。
9. 完成并发压测后再启用限时抢券。
10. 稳定运行并完成至少一次日终对账后，逐步扩大活动规模。

回滚应用版本前必须确认新版本没有正在运行活动或 `LOCKED` 用户券。数据库迁移包含新订单金额语义，不能仅回滚 Java 而保留旧金额代码；需要向前修复或使用经过验证的兼容版本。

## 16. 完成检查

- 权限种子、角色授权、`CurrentUserView` 和前端菜单一致。
- 平台与店铺管理入口、路径和数据范围没有混用。
- 活动发布前校验能阻止所有结构化规则错误。
- 用户每个失败状态有稳定原因和可执行下一步。
- 抢券监控能区分售罄、限领、风控和依赖异常。
- 客服可从用户券号追踪到领取、交易、订单、退款和返券。
- 商家可区分买家实付、平台补贴和本店让利。
- 平台对账能验证发行、预算、核销、订单、退款和结算全链路。
- 所有异常恢复走任务或专用受审计工具，不直接改状态和金额。
